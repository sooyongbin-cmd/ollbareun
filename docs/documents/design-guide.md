# 올바름 인력관리시스템 디자인 가이드

| 항목 | 내용 |
| --- | --- |
| 문서 유형 | 전사 공통 디자인 시스템 및 화면 설계 가이드 |
| 적용 대상 | 회사소개 홈페이지, 관리자 웹, 현장 근무자 모바일 웹, 인증·오프라인·설치 화면 |
| 기술 기준 | Next.js App Router, Tailwind CSS v4, shadcn/ui `new-york`, Radix UI, Lucide Icons, Recharts |
| 구현 기준 | `components.json`, `src/app/globals.css`, `src/components/ui`, 각 영역 공통 레이아웃 |
| 기준 문서 | 요구사항분석서, 기능명세서, 화면명세서, 테스트계획서 |

## 1. 목적과 적용 원칙

이 문서는 관리자 대시보드에 도입한 shadcn/ui 기반 화면 구조를 특정 화면의 스타일로 한정하지 않고, 올바름 시스템 전체에서 재사용하는 공통 설계 기준으로 정의한다.

- 업무 정보를 빠르게 찾을 수 있도록 명확한 정보 위계와 일관된 상호작용을 제공한다.
- 장식보다 가독성, 충분한 여백, 상태의 명확성, 오류 복구 가능성을 우선한다.
- 관리자·현장 근무자·회사소개 화면은 서로 다른 밀도를 사용하되 같은 색상, 글꼴, 상태 표현, 접근성 원칙을 공유한다.
- 색상이나 아이콘만으로 의미를 전달하지 않고 텍스트 라벨, 상태명, 안내 문구를 함께 제공한다.
- 신규 화면과 개편 화면은 shadcn/ui 공통 컴포넌트를 우선 사용한다. 기존 화면은 기능 변경 시 공통 컴포넌트로 단계적으로 전환한다.
- 서버 데이터, 인증, 권한, PWA 동작과 시각 컴포넌트를 분리하여 디자인 변경이 업무 규칙을 바꾸지 않도록 한다.
- PC와 모바일에서 메뉴 위치나 배치는 달라질 수 있지만 업무 용어, 경로, 상태 의미는 동일하게 유지한다.

## 2. 디자인 시스템 구조

### 2.1 기술 구성

| 계층 | 기준 |
| --- | --- |
| 스타일 엔진 | Tailwind CSS v4와 CSS Custom Properties를 사용한다. |
| UI 프리미티브 | shadcn/ui `new-york` 스타일과 Radix UI를 사용한다. |
| 아이콘 | Lucide Icons를 기본 아이콘 체계로 사용한다. |
| 차트 | Recharts를 shadcn `ChartContainer`와 함께 사용한다. |
| 컴포넌트 위치 | 공통 UI는 `src/components/ui`, 업무 컴포넌트는 해당 기능 영역에 둔다. |
| 클래스 결합 | 조건부 스타일은 `src/lib/utils.ts`의 `cn()`을 사용한다. |
| 설정 | shadcn 설정은 루트의 `components.json`을 단일 기준으로 사용한다. |

shadcn/ui는 외부 컴포넌트 패키지를 그대로 소비하는 방식이 아니라, 프로젝트가 컴포넌트 소스 코드를 직접 소유하고 수정하는 방식으로 운영한다. 공통 컴포넌트를 수정할 때는 해당 변경이 관리자, 현장 근무자, 회사소개 화면에 미치는 영향을 함께 검토한다.

### 2.2 컴포넌트 선택 원칙

- HTML 요소를 직접 조합하기 전에 `Button`, `Card`, `Table`, `Badge`, `Alert`, `Sheet`, `Tooltip`, `Separator`, `Skeleton` 등 공통 컴포넌트가 있는지 확인한다.
- 기능별 화면은 공통 컴포넌트를 조합하여 만들고, 같은 형태의 카드·표·버튼을 화면마다 다시 구현하지 않는다.
- 공통 컴포넌트의 기본 동작과 접근성을 유지하면서 업무별 차이는 `variant`, 속성, 조합 컴포넌트로 표현한다.
- 삭제 등 복구가 어려운 동작에는 일반 `Dialog`가 아니라 확인 목적의 `AlertDialog` 패턴을 사용한다.
- 공통 컴포넌트에 없는 색상·간격·상태가 필요하면 화면 내부에 임의 값을 반복하지 않고 디자인 토큰을 먼저 확장한다.

## 3. 색상과 디자인 토큰

### 3.1 브랜드 색상

| 토큰/용도 | 기준값 | 적용 |
| --- | --- | --- |
| Primary | `#0066cc` | 주요 버튼, 활성 메뉴, 링크, 핵심 지표 |
| Primary Focus | `#0071e3` | 키보드 포커스와 입력 포커스 |
| Primary Hover | `#0077ed` | 주요 동작의 마우스 오버 |
| Canvas / Background | `#ffffff` | 페이지 기본 배경 |
| Canvas Parchment / Muted | `#f5f5f7` | 보조 배경, 필터, 비활성 영역 |
| Surface Pearl | `#fafafc` | 약한 구분이 필요한 표면 |
| Ink / Foreground | `#1d1d1f` | 제목과 본문 |
| Ink Muted | `#6e6e73`~`#7a7a7a` | 설명, 보조 정보, 비활성 정보 |
| Border / Hairline | `#e0e0e0`~`#e5e7eb` | 카드, 표, 입력창 경계 |
| Destructive | `#d92d20` | 삭제, 실패, 복구가 어려운 동작 |

- 실제 구현값은 `src/app/globals.css`를 단일 기준으로 한다.
- shadcn 의미 기반 토큰인 `background`, `foreground`, `card`, `muted`, `accent`, `border`, `ring`, `sidebar`를 브랜드 색상에 매핑한다.
- 기반 표면에는 `bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `border-border`를 사용한다.
- 상태색은 반드시 상태 텍스트 또는 아이콘과 함께 사용한다.
- 다크 모드는 현재 기본 범위에 포함하지 않는다. 향후 도입 시 개별 화면의 색상을 반전하지 않고 동일한 의미 기반 토큰에 다크 값을 추가한다.

### 3.2 차트 색상

- 첫 번째 시리즈는 `--chart-1`의 Primary Blue를 사용한다.
- 두 번째 시리즈는 `--chart-2`의 Green 계열을 사용한다.
- 3개 이상의 시리즈가 필요할 때만 `--chart-3`~`--chart-5`를 순서대로 사용한다.
- 차트 색상만으로 시리즈를 구분하지 않고 범례, 툴팁, 축 라벨을 제공한다.
- 비율 차트의 Y축은 특별한 사유가 없으면 0~100% 범위를 사용한다.

## 4. 타이포그래피

- 기본 글꼴은 Pretendard Variable을 사용하며 시스템 폰트를 대체 글꼴로 둔다.
- `@theme inline`의 글꼴 선언은 자기 참조 CSS 변수를 사용하지 않고 실제 글꼴 이름을 선언한다.
- 기본 UI 본문은 14~17px 범위에서 화면 밀도에 맞춰 사용한다.
- 관리자 화면은 페이지 제목 24~32px, 섹션 제목 16~20px, 본문 14px를 기본으로 한다.
- 현장 근무자 화면은 가독성과 터치 환경을 고려해 본문과 주요 버튼을 17~22px까지 확대할 수 있다.
- 회사소개 화면의 대표 제목은 콘텐츠 위계를 위해 더 크게 사용할 수 있지만 모바일 줄바꿈을 함께 검증한다.
- 입력 라벨과 표 머리글은 12px 미만으로 축소하지 않는다.
- 수치, 시간, 비율은 `tabular-nums`를 사용하고 필요한 경우 고정폭 글꼴을 적용한다.
- 한 화면 안에서 제목, 버튼, 입력 라벨의 굵기 체계를 일관되게 유지한다.

## 5. 간격, 크기, 모서리

- 기본 관리자 화면은 `gap-4`, `gap-6`, `p-4`, `p-6` 중심의 편안한 밀도를 사용한다.
- 모바일 본문 여백은 16px, 태블릿 이상은 24px, 넓은 관리자 화면은 32px을 기준으로 한다.
- 카드 기본 모서리는 shadcn `rounded-xl`, 일반 컨트롤은 `rounded-md`~`rounded-lg`를 사용한다.
- 하나의 화면에서 임의의 모서리 값을 혼합하지 않는다.
- 주요 터치 대상은 최소 44×44px을 확보한다. 조밀한 관리자 도구는 보조 설명이나 툴팁을 제공하는 조건으로 축소할 수 있다.
- 카드 안에 카드를 반복해서 중첩하지 않는다. 정보 그룹은 `Separator`, 제목, 여백으로 구분한다.
- 큰 그라데이션이나 글래스 효과를 기반 화면 전체에 사용하지 않는다. 요약 카드의 미세한 Primary tint처럼 정보 위계를 돕는 범위에서만 사용한다.

## 6. 시스템 영역별 레이아웃

### 6.1 관리자 웹

관리자 화면은 shadcn `SidebarProvider`, `Sidebar`, `SidebarInset` 기반의 전체 높이 업무 쉘을 표준으로 한다.

- 데스크톱에서는 좌측 사이드바, 상단 헤더, 본문 inset 구조를 사용한다.
- 사이드바는 펼침 상태와 아이콘 축소 상태를 지원한다.
- 축소 상태에서도 각 화면으로 이동할 수 있는 아이콘을 남기고 아이콘 의미를 설명하는 `Tooltip`을 제공한다.
- 현재 경로는 활성 메뉴 스타일로 표시하며, 상단 헤더에는 동일한 메뉴 설정을 사용한 breadcrumb를 제공한다.
- 메뉴 이름, 경로, 아이콘은 하나의 탐색 설정에서 관리하고 데스크톱·모바일·breadcrumb가 이를 공유한다.
- 모바일에서는 사이드바를 `Sheet`로 전환한다. 메뉴 선택, 배경 선택, 닫기 버튼, Escape 키로 닫을 수 있어야 한다.
- 모바일 메뉴가 열려 있는 동안 본문 스크롤을 잠그고 포커스가 메뉴 밖으로 이탈하지 않게 한다.
- 본문은 `max-w-[1600px]` 범위에서 업무 표와 차트를 수용하고, 작은 화면에서는 안전한 내부 스크롤을 제공한다.
- 기존 하위 업무 화면은 공통 쉘 안에서 동작하며, 개편 시 동일한 Card·Form·Table 규칙으로 단계적으로 전환한다.

### 6.2 관리자 대시보드

관리자 홈은 다음 순서와 구성 요소를 기준으로 한다.

1. 페이지 제목과 한 문장의 화면 설명
2. 핵심 운영 지표 카드
3. 기간별 통합 추이 차트
4. 현장별 또는 업무별 요약 표
5. 실시간 상태 표

- 요약 카드는 지표명, 값, 단위, 설명, 보조 아이콘을 포함한다.
- 현재 기준 지표는 전체 직원, 현재 출근, 교육 미이수, 오늘 출근율이다.
- 비율·인원 값은 카드마다 같은 위치와 정렬을 유지한다.
- 출근율과 안전교육 이수율은 한 차트의 두 시리즈로 비교하고 날짜 툴팁, 범례, 퍼센트 축을 제공한다.
- 표는 `Card` 내부에 배치하되 표 자체의 경계와 카드 경계를 중복해 강조하지 않는다.
- 목록의 상태는 `Badge`로 표현하고 상태명 텍스트를 함께 표시한다.
- API 응답과 데이터 타입은 화면 디자인 변경만으로 수정하지 않는다. 새로운 지표가 필요할 때만 별도 기능 요구사항으로 정의한다.

### 6.3 현장 근무자 모바일 웹

- 세로형 모바일 화면과 한 손 조작을 우선한다.
- 출근, 퇴근, 점검 완료처럼 핵심 업무 동작은 화면 하단 접근이 쉽고 충분한 터치 영역을 갖도록 한다.
- 위치, 카메라, 알림, NFC 등 권한이 필요한 기능은 권한 요청 목적과 거부 시 대안을 먼저 안내한다.
- 네트워크가 불안정한 환경을 고려해 처리 중, 재시도, 오프라인 상태를 명확히 표시한다.
- 텍스트 확대 설정이 적용되어도 버튼, 표, 상태 정보가 잘리거나 겹치지 않아야 한다.
- 관리자 화면과 같은 상태색·아이콘 의미를 사용하되, 현장 화면은 더 큰 글자와 단순한 정보 구조를 사용한다.

### 6.4 회사소개 홈페이지

- 대표 메시지, 서비스 강점, 사회적 가치, 상담 신청, 회사 정보 순으로 명확한 서사를 구성한다.
- 콘텐츠 중심 화면이므로 관리자 화면보다 넓은 여백과 큰 타이포그래피를 사용할 수 있다.
- 카드 영역은 모바일 1열, 넓은 화면 3열을 기본으로 한다.
- CTA에는 공통 Primary 색상과 Button 동작을 사용한다.
- 관리자 화면의 조밀한 테이블·사이드바 패턴을 마케팅 화면에 그대로 적용하지 않는다.

### 6.5 인증, 설치, 오프라인 화면

- 인증 화면은 하나의 주요 작업에 집중된 Card 구조를 사용한다.
- 오류는 입력값 근처 또는 `Alert`로 제공하고 다시 시도할 방법을 명확히 안내한다.
- PWA 설치 안내는 일반 콘텐츠와 구분되는 대화상자 또는 배너로 제공하며 강제로 설치를 요구하지 않는다.
- 오프라인 화면은 현재 상태, 사용할 수 없는 기능, 재연결 또는 재시도 방법을 포함한다.
- 인증·세션 만료 시 사용자가 데이터가 삭제되었다고 오해하지 않도록 재로그인 안내를 제공한다.

## 7. 공통 컴포넌트 사용 기준

| 컴포넌트 | 적용 기준 |
| --- | --- |
| `Button` | 저장·등록·실행 등 주요 동작에 사용한다. 화면당 기본 Primary 동작은 최소화한다. |
| `Card` | 요약 지표, 차트, 표, 설정 그룹처럼 독립된 정보 단위에 사용한다. |
| `Table` | 구조화된 업무 목록에 사용하고 헤더, 빈 상태, 모바일 대응을 제공한다. |
| `Badge` | 출근·퇴근, 완료·미이수, 활성·비활성처럼 짧은 상태에 사용한다. |
| `Alert` | 오류, 경고, 중요한 안내를 제목과 설명으로 제공한다. |
| `Sheet` | 모바일 메뉴, 모바일 필터, 보조 편집 패널에 사용한다. |
| `Tooltip` | 축소된 아이콘이나 즉시 이해하기 어려운 조작을 설명한다. 필수 정보는 툴팁에만 두지 않는다. |
| `Separator` | 헤더, 메뉴, 정보 그룹 사이의 시각적 구분에 사용한다. |
| `Skeleton` | 카드·차트·표의 실제 구조를 반영한 로딩 상태에 사용한다. |
| `Input` | 항상 연결된 라벨, 필수 여부, 오류 안내와 함께 사용한다. |
| `Dialog` | 현재 흐름을 유지해야 하는 상세 입력·안내에 사용한다. |
| `AlertDialog` | 삭제 등 복구가 어려운 동작의 최종 확인에 사용한다. |

### 7.1 버튼과 동작

- Primary 버튼은 화면의 핵심 완료 동작에 사용한다.
- 보조 동작은 `secondary`, `outline`, `ghost` 중 중요도에 맞게 선택한다.
- 파괴적 동작은 `destructive` 의미를 사용하고 확인 절차를 제공한다.
- 아이콘 단독 버튼은 접근 가능한 이름과 툴팁을 제공한다.
- 비동기 처리 중에는 버튼을 비활성화하고 진행 상태를 표시해 중복 실행을 방지한다.

### 7.2 폼

- 라벨, 입력 요소, 도움말, 오류 문구를 하나의 필드 그룹으로 구성한다.
- placeholder를 라벨 대신 사용하지 않는다.
- 필수 입력은 시각적 표기와 검증 메시지를 함께 제공한다.
- 제출 오류 발생 시 첫 오류 위치로 이동하거나 사용자가 쉽게 찾을 수 있도록 표시한다.
- 저장 성공과 실패를 색상만이 아닌 문장으로 알린다.

### 7.3 표와 목록

- 표 머리글은 각 열의 의미를 명확히 표현한다.
- 정렬 가능한 열은 정렬 상태와 방향을 키보드 및 보조기술에 전달한다.
- 모바일에서는 데이터 성격에 따라 카드형 행 전환 또는 가로 스크롤 영역을 사용한다.
- 가로 스크롤을 사용할 경우 페이지 전체가 아니라 표 컨테이너만 스크롤되어야 한다.
- 빈 결과는 빈 행만 남기지 않고 원인과 다음 행동을 설명한다.
- 로딩 중에는 기존 데이터를 갑자기 제거하기보다 Skeleton 또는 진행 상태를 제공한다.

### 7.4 차트

- 차트에는 제목, 설명, 축 단위, 범례, 툴팁을 제공한다.
- 차트만으로 업무 판단을 강제하지 않고 핵심 값 또는 표 형태의 대안을 제공한다.
- 모바일에서 차트가 화면 폭을 넘지 않게 `min-w-0`, `w-full`, 고정 높이를 함께 사용한다.
- 애니메이션은 짧고 절제되게 사용하며 `prefers-reduced-motion` 환경을 고려한다.

## 8. 상태 설계

모든 데이터 기반 화면은 다음 네 가지 상태를 설계한다.

| 상태 | 표현 기준 |
| --- | --- |
| Loading | 실제 콘텐츠 형태와 유사한 Skeleton 또는 명시적 진행 상태 |
| Empty | 데이터가 없는 이유와 가능한 다음 작업 |
| Error | 문제 설명, 영향 범위, 재시도 또는 이동 방법 |
| Success | 완료 결과와 후속 행동을 짧은 문장으로 안내 |

- 로딩 중 레이아웃 크기가 크게 변하지 않도록 카드·표·차트 영역을 미리 확보한다.
- API 오류 메시지를 그대로 노출하기 전에 사용자가 이해할 수 있는 문장으로 변환한다.
- 빈 상태와 오류 상태를 같은 문구로 처리하지 않는다.
- 네트워크 재시도 시 사용자가 입력한 값을 가능한 한 보존한다.

## 9. 접근성

- 모든 입력 요소에는 연결된 `label`을 제공한다.
- 페이지에는 하나의 명확한 `h1`을 두고 섹션 제목은 순서에 맞는 heading을 사용한다.
- 링크는 이동, 버튼은 동작에 사용한다.
- 키보드 포커스를 명확히 표시하고 메뉴, 대화상자, 표 정렬, 폼을 키보드로 조작할 수 있게 한다.
- 모달과 모바일 Sheet는 적절한 이름, 포커스 트랩, Escape 닫기, 닫힌 뒤 포커스 복귀를 제공한다.
- 텍스트와 배경은 WCAG AA 수준의 대비를 목표로 한다.
- 아이콘에는 장식용이면 `aria-hidden`, 의미가 있으면 접근 가능한 이름을 제공한다.
- 차트에는 `role="img"`와 차트 내용을 설명하는 이름을 제공하고 범례와 수치 정보를 함께 제공한다.
- 상태 변경은 필요한 경우 `role="status"` 또는 `role="alert"`로 전달한다.
- 200% 확대와 모바일 텍스트 확대에서도 핵심 기능을 사용할 수 있어야 한다.

## 10. 반응형 기준

| 구간 | 기본 동작 |
| --- | --- |
| 모바일, 768px 미만 | 1열 카드, Sheet 메뉴, 16px 본문 여백, 표 내부 스크롤 |
| 태블릿, 768px 이상 | 2열 요약 카드, 24px 본문 여백 |
| 데스크톱, 1280px 이상 | 축소 가능한 사이드바, 최대 4열 요약 카드, 표 2열 배치 가능 |

- 특정 기기명이 아니라 콘텐츠가 깨지는 지점을 기준으로 breakpoint를 선택한다.
- 모든 화면에서 `documentElement.scrollWidth`가 viewport 폭을 넘지 않는지 확인한다.
- 고정 폭은 차트 높이, 아이콘 크기처럼 의도가 명확한 경우에만 사용한다.
- 긴 이름, 이메일, 현장명은 `truncate`, 줄바꿈 또는 표 내부 스크롤 중 데이터 성격에 맞는 방식을 선택한다.

## 11. 탐색과 용어

- 관리자 메뉴의 기준 분류는 대시보드, 직원관리, 현장점검, 안전교육, 리포트출력, 시스템이다.
- 메뉴명과 화면 제목은 동일한 업무 용어를 사용한다.
- 현재 화면은 활성 메뉴와 breadcrumb로 동시에 확인할 수 있게 한다.
- 메뉴 설정은 단일 데이터 구조로 관리하고 같은 링크를 여러 컴포넌트에 중복 작성하지 않는다.
- 존재하지 않는 상위 화면으로 연결되는 가짜 링크를 만들지 않는다.
- 모바일과 데스크톱에서 메뉴 순서를 동일하게 유지한다.

## 12. 구현 규칙

- Next.js App Router의 Server Component를 기본으로 사용하고 상호작용이 필요한 가장 작은 영역에만 `"use client"`를 선언한다.
- 데이터 조회·인증·권한 검사는 기존 서버/API 계층을 유지하며 디자인 컴포넌트에 직접 결합하지 않는다.
- 공통 UI는 `@/components/ui`, 업무 컴포넌트는 해당 도메인 경로에서 import한다.
- 조건부 클래스는 문자열 수동 결합 대신 `cn()`을 사용한다.
- 기반 표면에 임의 hex 또는 Tailwind 팔레트 색상을 직접 반복하지 않는다.
- Lucide 아이콘은 기본 16~20px 범위에서 사용하고 한 화면에서 선 굵기와 크기를 통일한다.
- shadcn 컴포넌트를 추가할 때는 필요한 항목만 설치하고 예제 블록의 샘플 데이터와 불필요한 의존성을 그대로 포함하지 않는다.
- 공통 컴포넌트 소스를 수정할 경우 기존 사용처, 키보드 동작, 모바일 동작을 함께 테스트한다.

## 13. 검증과 완료 기준

신규 화면 또는 디자인 변경은 다음 항목을 모두 확인해야 완료로 본다.

- 핵심 업무 데이터와 기존 API 계약이 유지된다.
- Loading, Empty, Error, Success 상태가 구현되어 있다.
- 데스크톱과 모바일에서 가로 넘침과 잘림이 없다.
- 사이드바 펼침·축소, 모바일 Sheet, Escape 닫기, 스크롤 잠금이 정상 동작한다.
- 키보드 탐색과 포커스 표시가 정상 동작한다.
- 활성 메뉴와 breadcrumb가 현재 경로와 일치한다.
- 표 링크, 상태 Badge, 차트 범례와 툴팁이 정확하다.
- 관련 컴포넌트 테스트와 전체 회귀 테스트가 통과한다.
- 변경 파일 ESLint와 TypeScript 검사가 통과한다.
- 프로덕션 빌드가 필요한 환경변수 조건에서 성공한다.
- 브라우저 콘솔 오류와 Next.js 오류 오버레이가 없다.

권장 검증 화면 폭은 최소 모바일 390px, 태블릿 768px, 데스크톱 1440px이다.

## 14. 적용 및 변경 관리

### 14.1 현재 기준 구현

관리자 공통 쉘과 `/manager` 대시보드는 이 문서의 shadcn/ui 기반 구조를 구현한 기준 화면으로 사용한다. 관리자 하위 목록·등록·상세 화면과 현장 근무자·회사소개 화면은 기능 변경 또는 화면 개편 시 이 기준으로 단계적으로 통일한다.

### 14.2 적용 순서

1. 전역 토큰과 공통 컴포넌트를 재사용한다.
2. 각 영역의 공통 레이아웃과 탐색 구조를 통일한다.
3. 목록 화면의 Card·Form·Table·상태 표현을 전환한다.
4. 로딩·빈 상태·오류 상태를 공통 패턴으로 전환한다.
5. 모바일, 접근성, 회귀 테스트를 완료한다.

### 14.3 문서와 코드 변경

- 디자인 토큰 또는 공통 컴포넌트 변경 시 관리자, 현장 근무자, 회사소개 화면의 영향을 함께 확인한다.
- 신규 화면은 화면명세서에 화면 ID, 경로, 권한, 상태, 반응형 동작을 먼저 반영한다.
- 새로운 패턴이 두 화면 이상에서 반복되면 공통 컴포넌트 또는 이 문서의 기준으로 승격한다.
- 실제 구현과 문서가 다르면 코드만 예외로 남기지 말고 문서 또는 구현을 함께 갱신한다.
- 기존 화면의 단계적 전환 중에는 레거시 `.apple-*` 스타일과 shadcn 컴포넌트가 공존할 수 있지만, 한 화면 안에서는 하나의 밀도와 상태 체계를 유지한다.
