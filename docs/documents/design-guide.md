# 올바름 인력관리시스템 디자인 가이드

| 항목 | 내용 |
| --- | --- |
| 문서 유형 | 전사 공통 디자인 시스템 및 화면 설계 가이드 |
| 대상 | 회사소개 홈페이지, 관리자 웹, 현장 근무자 모바일 웹 |
| 디자인 기반 | shadcn/ui `new-york` 스타일 |
| 기술 기준 | Tailwind CSS v4, Radix UI, Lucide Icons, CSS Custom Properties |
| 구현 기준 | `components.json`, `src/components/ui`, `src/app/globals.css` |
| 기준 문서 | 요구사항분석서, 기능명세서, 화면명세서 |

## 1. 프로젝트 디자인 기반

올바름 인력관리시스템의 모든 사용자 화면은 **shadcn/ui를 기본 디자인 시스템으로 사용한다.** 이 기준은 관리자 화면에만 한정하지 않으며 회사소개 홈페이지, 관리자 웹, 현장 근무자 모바일 웹, 인증·설치·오프라인 화면을 포함한 프로젝트 전체에 적용한다.

- shadcn/ui는 Radix UI 기반의 `new-york` 스타일을 사용한다.
- 신규 화면과 개편 화면은 `Button`, `Card`, `Table`, `Badge`, `Alert`, `Dialog`, `Sheet`, `Tooltip`, `Separator`, `Skeleton`, `Input` 등 shadcn/ui 컴포넌트를 우선 사용한다.
- shadcn/ui 컴포넌트 소스는 `src/components/ui`에서 프로젝트가 직접 소유하고 관리한다.
- shadcn 설정은 루트의 `components.json`을 단일 기준으로 사용한다.
- 기반 표면과 상태 표현은 `background`, `foreground`, `card`, `muted`, `primary`, `border`, `ring`, `destructive` 등의 의미 기반 토큰을 사용한다.
- 조건부 클래스 결합에는 `src/lib/utils.ts`의 `cn()`을 사용한다.
- 아이콘은 Lucide Icons를 기본으로 사용하며 한 화면에서 크기와 선 굵기를 일관되게 유지한다.
- 기존 레거시 화면은 기능을 보존하면서 shadcn/ui 기반 컴포넌트로 단계적으로 전환한다.
- 공통 컴포넌트가 있는 경우 동일한 버튼·입력창·카드·표·모달을 화면별로 다시 구현하지 않는다.

## 2. 디자인 원칙

- 업무 정보를 빠르게 찾을 수 있도록 명확하고 일관된 화면을 제공한다.
- 관리자 화면은 목록·검색·입력 중심으로, 현장 근무자 화면은 한 손 조작이 쉬운 모바일 중심으로 설계한다.
- 장식보다 정보 위계, 충분한 여백, 읽기 쉬운 대비를 우선한다.
- 색상만으로 상태를 구분하지 않고 상태명과 안내 문구를 함께 제공한다.
- PC와 모바일에서 동일한 업무 의미와 용어를 유지한다.
- shadcn/ui 기본 동작과 접근성을 유지하고, 업무별 차이는 속성·variant·조합 컴포넌트로 표현한다.
- 디자인 변경이 인증, 권한, API 계약, 업무 규칙을 변경하지 않도록 시각 컴포넌트와 업무 로직을 분리한다.

## 3. 색상

| 용도 | 기준 |
| --- | --- |
| Primary | 주요 버튼, 활성 메뉴, 핵심 강조에 사용 |
| Canvas | 페이지 기본 배경 |
| Surface | 카드, 입력 영역, 표 배경 |
| Ink | 제목과 본문 기본 글자 |
| Muted | 설명, 보조 정보, 비활성 정보 |
| Hairline | 표와 입력창의 경계선 |
| Success/Warning/Error | 처리 결과와 주의·오류 상태 |

- 실제 색상값은 `src/app/globals.css`의 디자인 토큰을 우선 적용한다.
- 컴포넌트에 임의 색상을 추가하기보다 공통 토큰을 확장한다.

### 3.1 올바름 전용 Pantone 색상

올바름의 공식 전용색상은 다음 네 가지 Pantone CMYK Coated 색상을 원본 식별자로 사용한다.

| 원본 식별자 | 공식 sRGB/HEX | 시스템 직군 |
| --- | --- | --- |
| `PANTONE P 115-6 C` | Pantone Connect 확인 후 기록 | 명도·대비 분석 후 확정 |
| `PANTONE P 115-16 C` | Pantone Connect 확인 후 기록 | 명도·대비 분석 후 확정 |
| `PANTONE P 106-16 C` | Pantone Connect 확인 후 기록 | 명도·대비 분석 후 확정 |
| `PANTONE P 169-15 C` | Pantone Connect 확인 후 기록 | 명도·대비 분석 후 확정 |

- Pantone 식별자는 인쇄 원본을 관리하기 위한 값이며 CSS 색상값으로 직접 사용하지 않는다.
- 웹과 앱에는 Pantone Connect의 `COLOR DATA`에서 확인한 공식 sRGB/HEX 값을 사용한다. 임의 변환 사이트의 근사값을 브랜드 원색으로 확정하지 않는다.
- 공식 HEX 확보 후 상대 명도와 WCAG 대비를 계산해 `Primary`, `Secondary`, `Accent`, `Brand Dark` 직군을 배정한다.
- 공식 HEX가 확정되기 전까지 현재의 파란색 `primary` 토큰을 임시 디지털 기준색으로 유지한다.
- hover, active, muted, foreground 색상은 공식 원색에서 파생하되 텍스트와 아이콘은 WCAG AA 대비를 충족해야 한다.
- Pantone 원색은 `--brand-pantone-*` 원시 토큰으로 보존하고, 화면에서는 `primary`, `secondary`, `accent`, `foreground` 같은 의미 기반 토큰만 사용한다.
- 버튼, Badge, Chart, Alert 등에 Pantone HEX를 직접 작성하지 않는다. 공통 토큰을 변경하면 시스템 전체에 동일하게 반영되도록 한다.
- 인쇄물은 Pantone 실물 가이드와 출력 조건을 기준으로 별도 검수하며, 모니터 표시색과 인쇄 결과가 완전히 동일하다고 가정하지 않는다.

## 4. 타이포그래피

- 기본 글꼴은 Pretendard 계열을 사용한다.
- 페이지 제목은 32~40px, 섹션 제목은 20~24px, 본문은 15~17px를 권장한다.
- 입력 라벨과 표 머리글은 본문보다 작게 사용하되 12px 미만으로 축소하지 않는다.
- 제목, 버튼, 입력 라벨은 동일 화면에서 동일한 굵기 체계를 유지한다.

## 5. 레이아웃

### 5.1 관리자 화면

- PC에서는 좌측 사이드바와 본문 영역을 사용하고, 모바일에서는 햄버거 메뉴로 전환한다.
- 본문 최대 폭은 업무 화면 특성에 따라 980~1180px를 기준으로 한다.
- 목록 화면은 제목, 조회 조건, 주요 작업, 결과 목록 순으로 구성한다.
- 공통 쉘은 shadcn `Sidebar`, `Sheet`, `Tooltip`, `Separator`를 조합해 구성한다.
- 대시보드와 업무 화면은 shadcn `Card`, `Table`, `Badge`, `Alert`, `Skeleton`을 기본 구성 요소로 사용한다.

### 5.2 현장 근무자 화면

- 세로형 모바일 화면을 우선하며 주요 버튼은 충분한 터치 영역과 전체 폭을 확보한다.
- 위치·카메라·알림 등 권한이 필요한 기능은 요청 목적과 거부 시 대안을 안내한다.
- 처리 중에는 로딩 상태를 표시하고 중복 입력을 방지한다.

### 5.3 회사소개 홈페이지

- 대표 이미지와 핵심 메시지, 서비스 강점, 사회적 가치, 상담 신청, 회사 정보 순으로 구성한다.
- 카드 영역은 모바일 1열, 넓은 화면 3열을 기본으로 한다.

### 5.4 모바일 목록형 데이터

- 관리자 웹, 현장 근무자 웹, 회사소개 및 기타 사용자 화면의 **모든 목록형 데이터는 768px 미만 모바일 화면에서 공통적으로 카드 형태로 표시한다.**
- 데스크톱과 태블릿에서는 shadcn `Table`의 행·열 구조를 유지하고, 모바일에서는 한 개의 데이터 행을 한 개의 독립된 `Card` 단위로 전환한다.
- 모바일 카드 안에서는 각 값의 항목명을 `data-label`로 함께 표시해 데스크톱 표 머리글과 동일한 의미를 유지한다.
- 카드 간에는 명확한 간격을 두고 `card`, `border`, `muted-foreground` 등 의미 기반 토큰을 사용한다.
- 긴 텍스트, 상태 Badge, 링크와 작업 버튼은 카드 너비 안에서 줄바꿈되며 화면 밖으로 잘리지 않아야 한다.
- 빈 목록은 빈 카드를 반복하지 않고 목록 영역 전체를 사용하는 하나의 명확한 empty state로 표시한다.
- 단일 열 목록은 중복된 항목명을 표시하지 않고 콘텐츠 자체를 카드 본문으로 사용한다.
- 모바일 목록의 기본 표현을 가로 스크롤 테이블로 대체하지 않는다. 비교를 위해 가로축 유지가 필수인 비목록형 매트릭스·일정표·차트만 별도 설계한다.
- 이 동작은 화면별 CSS가 아니라 `src/components/ui/table.tsx`와 공통 반응형 스타일에서 관리한다.

## 6. 공통 컴포넌트

| 컴포넌트 | 적용 기준 |
| --- | --- |
| `Button` | 저장·등록·실행 등 주요 동작에 사용하며 배경색과 글자색이 함께 정의된 variant를 명시적으로 선택한다. |
| `Card` | 요약 정보, 차트, 표, 입력 그룹처럼 독립된 정보 단위에 사용한다. |
| `Input` / `Textarea` | 연결된 라벨, 필수 여부, 도움말, 오류 문구와 함께 사용한다. |
| `Table` | 구조화된 업무 목록에 사용하고 머리글, 빈 상태를 제공하며 모바일에서는 행 단위 Card로 전환한다. |
| `Badge` | 완료·미완료, 출근·퇴근, 활성·비활성처럼 짧은 상태에 사용한다. |
| `Alert` | 성공·경고·오류·중요 안내를 제목과 설명으로 제공한다. |
| `Dialog` | 현재 흐름을 유지해야 하는 입력·안내에 사용한다. |
| `AlertDialog` | 삭제 등 복구가 어려운 동작의 최종 확인에 사용한다. |
| `Sheet` | 모바일 메뉴, 필터, 보조 작업 패널에 사용한다. |
| `Skeleton` | 실제 콘텐츠 구조를 반영한 로딩 상태에 사용한다. |

### 6.1 버튼 variant와 색상 대비

- shadcn/ui `Button`의 기본 variant는 `bg-primary`와 `text-primary-foreground`를 하나의 시각 계약으로 제공한다. 기본 variant에서 배경만 `bg-background`, `bg-white`, `bg-muted`, `bg-secondary`, `bg-transparent` 등으로 덮어쓰지 않는다. 배경만 밝게 바꾸면 기본의 밝은 글자색이 남아 버튼 문구가 보이지 않을 수 있다.
- 주요 실행 동작은 `default`, 밝은 배경의 보조 동작은 `outline`, 조용한 아이콘·도구 동작은 `ghost`, 텍스트형 이동은 `link`, 위험 동작은 `destructive`를 사용한다.
- `className`은 너비, 간격, 정렬처럼 variant가 제공하지 않는 레이아웃 조정에 우선 사용한다. 배경색·글자색·테두리를 조합해 기존 variant를 화면마다 다시 만들지 않는다.
- 링크를 버튼처럼 표시할 때도 `Button asChild`에 용도에 맞는 variant를 명시한다.
- 기본, hover, focus, disabled 상태 모두에서 텍스트와 배경은 WCAG AA 수준의 대비를 유지한다.
- 시스템 전역 회귀 테스트는 밝은 배경이나 입력형 테두리를 직접 지정한 `Button`에 명시적 variant가 있는지 검사한다.

## 7. 접근성 및 반응형

- 모든 입력 요소에 연결된 라벨을 제공한다.
- 키보드 포커스를 시각적으로 표시하고 버튼과 링크를 키보드로 실행할 수 있게 한다.
- 텍스트와 배경은 WCAG AA 수준의 대비를 목표로 한다.
- 모바일의 목록형 표는 행 단위 카드로 전환하고 각 값에 항목명을 함께 표시한다.
- 이미지에는 용도를 설명하는 대체 텍스트를 제공한다.

## 8. 변경 관리

- 공통 토큰이나 컴포넌트 변경 시 관리자·근무자·회사소개 화면의 영향을 함께 확인한다.
- 신규 화면은 `화면명세서.md`에 화면 ID와 동작을 먼저 반영한다.
- 구현 검수 시 PC, 모바일, 키보드 조작, 권한 거부 상태를 포함한다.
- 신규 UI는 shadcn/ui 적용을 기본 완료 조건으로 검토한다.
- 필요한 컴포넌트만 프로젝트에 추가하고 예제 블록의 샘플 데이터나 불필요한 의존성을 포함하지 않는다.
- `src/components/ui`의 공통 컴포넌트를 수정할 때는 기존 관리자·근로자·공개 화면의 회귀 테스트를 함께 수행한다.
- 레거시 스타일과 shadcn/ui가 전환 기간 동안 공존할 수 있으나, 하나의 화면 안에서는 동일한 밀도·모서리·상태 표현 체계를 유지한다.

## 9. 시스템 전체 shadcn/ui new-york 전면 개편 계획

### 9.1 공통 기반

- 기존 `components.json`의 Radix 기반 `new-york` 설정을 단일 기준으로 유지한다.
- 화면에서 실제로 필요한 shadcn/ui 컴포넌트만 추가하고 예제 데이터와 불필요한 의존성을 포함하지 않는다.
- 공통 페이지 헤더, 조회 조건, 데이터 표, 폼 필드, 상태 Badge, 로딩·오류·빈 상태를 조합 컴포넌트로 표준화한다.
- 자체 모달과 삭제 확인은 각각 `Dialog`, `AlertDialog` 기반으로 교체한다.
- 레거시 색상과 임의 HEX를 의미 기반 토큰으로 전환하되 공식 Pantone HEX가 확정될 때까지 현재 파란색을 임시 `primary`로 사용한다.

### 9.2 관리자 웹

- 기존 Sidebar, 모바일 Sheet, Header, Dashboard를 관리자 화면의 표준 쉘로 유지한다.
- 목록은 `PageHeader → 조회 조건 Card → Table`, 등록·수정은 `PageHeader → Form Card → 작업 버튼`, 상세는 핵심 정보와 관련 데이터 Card 순서로 통일한다.
- 로딩은 콘텐츠 형태의 Skeleton, 오류는 Alert, 상태는 Badge, 삭제는 AlertDialog로 표현한다.
- 잘못 표기된 `/manager/safety/*`는 `/manager/safety/*`로 정리하고 기존 URL은 영구 리다이렉트로 호환한다.
- API, 인증, 엑셀, QR/NFC, 교육과 알림의 업무 계약은 변경하지 않는다.

### 9.3 현장 근로자 앱

- `/guard`의 공통 제품 명칭은 “현장 근로자”로 사용하고 경비원·미화원은 실제 직군 Badge로 구분한다.
- 모바일 화면은 상단 상태 영역, 본문, 홈·출퇴근·업무·내 정보 하단 탐색으로 구성한다.
- 직군별 작업 홈을 제공하고 기존 출퇴근, QR, NFC, 특이사항, 교육, 프로필 딥링크를 유지한다.
- 모든 주요 터치 영역은 최소 48px로 구성하고 위치·카메라·NFC·알림 권한의 거부와 미지원 상태에 대안을 제공한다.
- 현재의 확대·글자 크기, 세션, 패스키, PWA 설치 동작은 보존한다.

### 9.4 공개·인증·오프라인 화면

- 회사소개 홈페이지는 마케팅 정보 구조를 유지하면서 Card, Button, Dialog, Input, Textarea, Progress로 재구성한다.
- 관리자 및 현장 근로자 인증은 Card 중심의 일관된 인증 화면으로 구성한다.
- PWA 설치, 인앱 브라우저, 오프라인 안내를 접근 가능한 Dialog, Alert, Button 조합으로 통일한다.

### 9.5 완료 조건

- 사용자 화면에서 raw 버튼·입력·선택·표·모달의 중복 구현을 제거하고 shadcn/ui 또는 공통 조합 컴포넌트를 사용한다.
- 더 이상 사용하지 않는 `.button-primary`, `.button-secondary`, `.field`, `.apple-table`, `.status-*` 레거시 스타일을 제거한다.
- `npm test`, `npm run lint`, `npm run build`가 모두 통과해야 한다.
- 390px, 768px, 1440px에서 주요 화면을 검수하고 키보드 조작, 포커스, 스크롤, safe-area, 표 오버플로를 확인한다.
- 공식 Pantone HEX가 제공되면 토큰 대응표, 대비 결과, 컴포넌트 적용 결과를 본 문서와 `globals.css`에 함께 반영한다.
