관리자 승인 기반 Passkey 로그인 구현 계획_20260608 ​

Summary ​

  • /guard는 기존 이름/전화번호 로그인을 유지하고, 로그인 후 경비원이 “패스키 등록 요청”을 보낼 수 있게 한다.
  • 관리자가 승인하면 서버가 해당 경비원에게 Supabase Auth 계정을 연결하고, 경비원은 승인된 상태에서 1회 등록 링크/세션을 통해 registerPasskey()를 실행한다.
  • 이후 /guard 로그인 화면에는 “패스키로 로그인” 버튼을 추가하고, 성공 시 Supabase Auth user.id를 employees.auth_user_id에 매핑해 기존 GuardSession 형태로 전환한다.
  • Supabase Passkey는 현재 beta/experimental 기능이므로 기존 이름/전화번호 로그인은 fallback으로 계속 둔다.

Key Changes ​

DB ​

  • employees에 auth_user_id uuid unique null, passkey_enabled boolean default false 추가.
  • guard_passkey_requests 테이블 추가: employee_id, status(pending|approved|rejected|registered|revoked), requested_at, reviewed_at, reviewed_by, registered_at.
  • RLS는 관리자/서버 API 경유만 허용하고, 클라이언트 직접 쓰기는 막는다.

Supabase Auth ​

  • Dashboard에서 Authentication → Passkeys 활성화.
  • RP ID는 운영 도메인으로 고정: 기본값 ollbareun.vercel.app.
  • RP Origins: https://ollbareun.vercel.app, 개발용 http://localhost:3000.
  • 서버 전용 SUPABASE_SECRET_KEY를 추가하고, service role/secret key는 브라우저에 노출하지 않는다.

Client/Auth ​

  • 기존 src/lib/supabase.ts는 데이터용으로 유지.
  • Passkey 전용 client를 별도 생성: experimental: { passkey: true }, persistSession: true.
  • 등록 완료 후에는 Supabase Auth 세션을 signOut()하고, 앱은 기존 sessionStorage 기반 GuardSession을 계속 사용한다.

Implementation Changes ​

/guard/main/profile ​

  • “패스키 등록 요청” 섹션 추가.
  • 요청 상태 표시: 미요청, 승인 대기, 승인됨, 등록 완료, 거절됨.
  • 승인됨 상태에서는 “이 기기에 패스키 등록” 버튼을 표시한다.

관리자 화면 ​

  • 직원 관리 또는 별도 메뉴에 “패스키 요청 관리” 목록 추가.
  • 요청자 이름/전화번호/요청일/상태 표시.
  • 승인/거절/해제 버튼 제공.

API ​

  • POST /api/guard/passkey-requests: 기존 경비원 세션의 employee.id로 요청 생성.
  • GET /api/guard/passkey-requests/me: 경비원 본인 요청 상태 조회.
  • PATCH /api/manager/guard-passkey-requests/[id]: 관리자 승인/거절/해제.
  • POST /api/guard/passkeys/registration-link: 승인된 경비원만 호출 가능. 서버가 Supabase Auth 사용자 생성/연결 후 일회성 Auth 링크를 발급.
  • POST /api/guard/passkeys/session: signInWithPasskey() 성공 후 Supabase access token을 검증하고 기존 GuardSession 응답 생성.

/guard ​

  • 기존 이름/전화번호 폼 위 또는 아래에 “패스키로 로그인” 버튼 추가.
  • 클릭 시 supabase.auth.signInWithPasskey() 실행.
  • 성공하면 /api/guard/passkeys/session으로 경비원 세션을 받아 sessionStorage["ollbareun.guard.session"]에 저장하고 /guard/main으로 이동.
  • 실패 시 기존 로그인 방식을 안내한다.

Test Plan ​

Unit/API tests ​

  • 미승인 경비원은 등록 링크 발급 불가.
  • 승인된 요청은 Auth 사용자와 employees.auth_user_id가 연결됨.
  • 등록 완료 후 요청 상태가 registered로 변경됨.
  • Passkey 로그인 성공 시 기존 GuardSession 형태가 반환됨.
  • 퇴직 직원, 미등록 직원, auth_user_id 미매핑 사용자는 거부됨.

Component tests ​

  • /guard에 패스키 로그인 버튼이 보임.
  • 패스키 실패 시 오류 메시지를 표시하고 기존 로그인 폼은 유지됨.
  • /guard/main/profile에서 상태별 버튼/문구가 올바르게 보임.
  • 관리자 요청 목록에서 승인/거절 액션이 호출됨.

Manual verification ​

  • http://localhost:3000에서 개발용 Origin으로 등록 테스트.
  • 운영 배포 후 https://ollbareun.vercel.app에서 실제 기기 지문/Face ID/PIN 등록 및 로그인 테스트.
  • RP ID 변경 없이 운영 도메인이 고정되어 있는지 확인.

Assumptions ​

  • 관리자 인증은 현재 관리자 화면 접근 방식과 동일한 수준으로 보호한다고 가정한다.
  • 관리자 승인 방식은 SMS/이메일 본인확인을 하지 않으므로, 운영상 관리자가 실제 경비원 요청인지 확인해야 한다.
  • Supabase Passkey API는 beta/experimental이므로 이름/전화번호 로그인은 제거하지 않는다.
  • 운영 RP ID 기본값은 ollbareun.vercel.app으로 잡고, 실제 커스텀 도메인이 생기면 첫 등록 전에 최종 도메인으로 바꾼다.
