로그인 세션 관리 설명서 ​

1. 개요 ​

올바름 인력관리시스템은 근무자와 관리자의 로그인 상태를 브라우저를 닫은 후에도 복원한다. 로그인 상태에는 고정된 사용 만료 시간을 두지 않지만, 저장된 로그인 정보와 실제 업무 권한을 분리하여 매번 서버에서 현재 권한을 확인한다.

로그인 상태는 사용자가 로그아웃하거나 브라우저의 사이트 데이터를 삭제할 때까지 유지될 수 있다. 다만 퇴직, 계정 삭제 또는 관리자 권한 회수 시에는 저장된 세션이 남아 있어도 보호 화면과 업무 API를 이용할 수 없다.

2. 근무자 로그인 ​

2.1 이름과 연락처 로그인 ​

근무자는 /guard에서 이름과 연락처를 입력하여 로그인한다. 서버는 employees 테이블에서 이름과 정규화된 연락처가 일치하는 직원을 조회하며 다음 조건을 확인한다.

  • 등록된 직원이어야 한다.
  • 퇴직 처리되지 않은 직원이어야 한다.

인증에 성공하면 직원 정보와 함께 현재 날짜 기준 근무지 배정, 근무지 정보 및 당일 근태 정보를 조회하여 근무자 세션을 만든다. 로그인 성공과 실패 결과는 근무자 세션 로그에 기록된다.

2.2 Passkey 로그인 ​

등록된 근무자는 Passkey로도 로그인할 수 있다. Passkey 인증으로 발급된 Supabase access token을 서버에서 검증하고, 연결된 직원이 현재 이용 가능한 상태인지 확인한 후 동일한 근무자 세션을 생성한다.

2.3 저장되는 정보 ​

근무자 세션은 브라우저 localStorage의 다음 키에 JSON 형식으로 저장된다.

text
ollbareun.guard.session

세션에는 다음 정보가 포함된다.

  • 직원 정보
  • 현재 유효한 근무지 배정
  • 배정된 근무지 정보
  • 현재 또는 당일 근태 정보
  • 로그인 세션 로그 ID
  • 최초 생성 시각 createdAt
  • 마지막 사용 시각 lastActiveAt

근무자 이름은 다음 로그인 입력을 편리하게 하기 위해 별도 키에 저장된다.

text
ollbareun.guard.name

createdAt과 lastActiveAt은 세션 상태를 확인하기 위한 기록값이며, 해당 시각을 기준으로 세션을 자동 만료시키지는 않는다.

3. 근무자 세션 복원과 검증 ​

3.1 자동 복원 ​

근무자가 /guard에 접속했을 때 유효한 로컬 세션이 있으면 /guard/main으로 이동한다. 브라우저나 탭을 닫았다가 다시 실행해도 localStorage가 유지되어 있으면 로그인 화면을 거치지 않고 기존 세션을 복원한다.

과거 버전에서 sessionStorage에 저장한 세션이 발견되면 현재 형식의 localStorage로 자동 이전한다. 저장값이 손상되었거나 직원 ID가 없으면 해당 세션을 삭제하고 로그인 화면을 표시한다.

3.2 서버 재검증 ​

근무자 메인 화면에 진입하면 저장된 직원 ID로 서버에 세션 검증을 요청한다. 서버는 직원의 현재 상태를 확인하고 최신 배정, 근무지 및 근태 정보를 반환한다.

  • 검증 성공: 최신 서버 정보로 로컬 세션을 갱신한다.
  • 직원 삭제 또는 퇴직: 로컬 세션을 삭제하고 /guard로 이동한다.
  • 일시적인 네트워크 또는 서버 오류: 로컬 세션을 즉시 삭제하지 않고 다음 검증 기회를 기다린다.

출근, 퇴근, 교육 이수, 현장점검, 특이사항 보고 및 Push 구독 등 주요 업무 API도 처리 전에 직원의 존재 여부와 퇴직 여부를 다시 확인한다. 이용할 수 없는 직원의 요청은 HTTP 403으로 거부한다.

4. 관리자 로그인과 세션 ​

관리자는 /manager/auth에서 Google 계정으로 로그인한다. Google 인증 결과는 Supabase Auth가 처리하며, 인증 콜백에서 다음 순서로 관리자 권한을 확인한다.

  1. Supabase 인증 사용자를 확인한다.
  2. 사용자 ID가 admin_users에 등록되어 있는지 확인한다.
  3. 사전 등록된 이메일이 있고 아직 사용자 ID가 연결되지 않았다면 최초 로그인 사용자를 연결한다.
  4. 등록되지 않은 계정이면 Supabase 세션을 종료하고 관리자 로그인 화면으로 이동한다.

등록된 관리자가 로그인하면 Supabase의 access token과 refresh token을 기반으로 세션이 유지된다. 브라우저를 다시 실행해도 인증 쿠키와 refresh token이 유효하면 로그인 상태를 복원한다.

관리자 보호 화면을 표시할 때마다 서버에서 Supabase 사용자와 admin_users 등록 상태를 확인한다. 인증이 적용된 관리자 API도 동일한 인증 함수를 사용하여 접근 권한을 검사하며, 관리자 계정 관리처럼 최고 관리자 전용인 기능은 super_admin 역할을 추가로 확인한다.

관리자 access token은 영구 토큰이 아니다. 토큰이 만료되면 Supabase가 refresh token을 이용해 갱신하며, refresh token이 폐기되거나 인증 세션이 더 이상 유효하지 않으면 다시 로그인해야 한다.

5. 권한 회수와 세션 종료 ​

5.1 근무자 퇴직 또는 삭제 ​

근무자가 퇴직 처리되거나 직원 정보가 삭제되면 다음 서버 검증에서 접근이 차단된다. 메인 화면 검증에서는 저장된 로컬 세션을 삭제하고 로그인 화면으로 이동하며, 주요 업무 API는 요청을 HTTP 403으로 거부한다.

퇴직 상태를 해제하거나 직원을 다시 등록해도 기존 세션의 사용을 보장하지 않는다. 이용 재개 시에는 다시 로그인하는 것을 원칙으로 한다.

5.2 관리자 삭제 또는 권한 회수 ​

관리자가 admin_users에서 삭제되면 Supabase 인증 세션이 브라우저에 남아 있더라도 관리자 권한 검증을 통과하지 못한다. 보호 화면과 관리자 API 접근이 차단되며 관리자 로그인 화면으로 이동한다.

5.3 근무자 로그아웃 ​

근무자 로그아웃은 다음 작업을 수행한다.

  1. 현재 브라우저의 Push 구독을 해제한다.
  2. 서버에 저장된 근무자 Push 구독 정보를 삭제한다.
  3. Passkey 로그인에 사용한 Supabase 세션을 종료한다.
  4. localStorage와 레거시 sessionStorage의 근무자 세션을 삭제한다.
  5. Push 등록 캐시를 삭제한다.
  6. 로그아웃 결과를 세션 로그에 기록하고 /guard로 이동한다.

Push 구독 해제에 실패하더라도 로그인 세션 삭제와 로그인 화면 이동은 계속 진행한다.

5.4 관리자 로그아웃 ​

관리자 화면의 로그아웃 버튼은 Supabase signOut()을 실행한 후 /manager/auth로 이동한다. 이후 보호 화면에 접근하면 관리자 인증을 다시 요구한다.

6. 세션이 유지되지 않는 경우 ​

다음 상황에서는 자동 로그인이 해제되거나 다시 로그인이 필요할 수 있다.

  • 사용자가 명시적으로 로그아웃한 경우
  • 브라우저의 쿠키, 로컬 저장소 또는 사이트 데이터를 삭제한 경우
  • 시크릿 모드 종료 등 브라우저가 저장 데이터를 폐기한 경우
  • 다른 기기나 관리 기능에서 Supabase 인증 세션을 폐기한 경우
  • refresh token이 만료되거나 무효화된 경우
  • 근무자가 퇴직·삭제되거나 관리자가 admin_users에서 삭제된 경우
  • 저장된 근무자 세션 데이터가 손상되었거나 직원 ID가 없는 경우

따라서 이 시스템의 장기 로그인은 브라우저에 저장된 인증 정보가 유효하고 사용자의 현재 업무 권한이 유지되는 동안 제공된다.

7. 운영 확인 사항 ​

세션 관련 문의를 처리할 때는 다음 순서로 확인한다.

  1. 근무자는 employees에 존재하며 is_retired가 false인지 확인한다.
  2. 관리자는 Supabase Auth 사용자와 admin_users 등록 정보가 모두 존재하는지 확인한다.
  3. 브라우저에서 해당 사이트의 쿠키와 로컬 저장소가 차단되거나 삭제되지 않았는지 확인한다.
  4. 근무자 문제는 관리자 화면의 세션 로그에서 로그인, Push 등록 및 로그아웃 결과를 확인한다.
  5. 일시적인 네트워크 장애인지 확인한 후 다시 접속하여 서버 재검증을 수행한다.
