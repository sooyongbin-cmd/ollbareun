보안문제 ​

현재 로그인 세션 유지 구현은 단순히 로그인 상태가 오래 유지되는 문제를 넘어, 근무자 인증 구조 자체에 치명적인 보안 위험이 있다. 운영 환경에 적용하기 전에 보완이 필요하다.

예상되는 보안 문제 ​

위험심각도예상되는 문제
employeeId만으로 사용자 식별치명적브라우저 저장값의 직원 ID를 다른 직원 ID로 변경하면 다른 직원을 사칭할 가능성이 있다. 서버는 실제 로그인 증명 없이 재직 중인 ID인지만 확인한다.
인증 없는 업무 API치명적공격자가 다른 직원 ID를 이용하여 출퇴근, 점검 기록, 교육 이수, 특이사항 보고 등을 요청할 수 있다.
무기한 localStorage 보관높음공용 PC, 분실 기기 또는 브라우저 프로필을 공유하는 환경에서 로그아웃하기 전까지 계속 접근할 수 있다.
XSS 및 악성 확장 프로그램 노출높음localStorage는 JavaScript로 읽을 수 있어 저장된 직원 개인정보와 식별자가 유출될 수 있다.
세션 위변조 방지 없음높음createdAt, lastActiveAt 및 직원 정보가 단순 JSON 형식이므로 사용자가 자유롭게 변경할 수 있다.
로그아웃 후 재사용 가능높음로그아웃은 브라우저에 저장된 데이터만 삭제한다. 미리 복사한 employeeId는 서버에서 별도로 폐기되지 않아 계속 사용할 수 있다.
개인정보 조회 가능성높음세션 조회 API가 별도의 인증 없이 직원 ID를 전달받아 직원, 근무지 및 근태 정보를 반환한다.
계정 공유 및 대리 출퇴근높음이름과 전화번호는 비밀정보로 보기 어렵고, 한번 로그인한 기기가 계속 인증된 상태로 남는다.
장애 발생 시 오래된 화면 유지중간네트워크 오류가 발생하면 저장된 세션을 보존하므로 권한이 변경된 후에도 기존 개인정보가 화면에 남을 수 있다.
공격 탐지 및 세션 차단 어려움중간기기별 세션과 세션의 발급, 만료 및 폐기 상태가 없어 탈취된 세션을 특정하여 차단하기 어렵다.

현재 구현의 핵심 문제 ​

src/app/guard/guard-session-storage.ts에서는 전체 근무자 세션을 만료 시간 없이 localStorage에 저장한다.

src/app/guard/main/guard-session-gate.tsx에서는 저장된 세션 안의 employeeId를 서버에 전달하여 세션의 유효성을 확인한다.

서버의 src/app/api/guard/session/route.ts와 src/lib/active-employee.ts에서도 로그인 토큰이나 서명을 검증하지 않고 해당 직원이 현재 재직 중인지만 확인한다.

따라서 employeeId는 세션 토큰이 아닌 단순한 식별자임에도 현재 구현에서는 사실상 인증 수단처럼 사용되고 있다. 공격자가 유효한 직원 ID를 알아내거나 브라우저 저장값을 변경할 수 있다면 다른 직원으로 요청을 보낼 가능성이 있다.

권장 개선 사항 ​

다음 순서로 보안 구조를 개선하는 것을 권장한다.

  1. 로그인 성공 시 서버가 추측할 수 없는 세션 토큰을 발급한다.
  2. 세션 토큰은 HttpOnly, Secure, SameSite 속성이 설정된 쿠키에 저장한다.
  3. 모든 근무자 API는 요청 본문이나 URL의 employeeId를 신뢰하지 않고, 검증된 서버 세션에서 직원 ID를 가져온다.
  4. 세션에 유휴 만료 시간과 절대 만료 시간을 적용한다.
    • 유휴 만료 예시: 마지막 이용 후 8~12시간
    • 절대 만료 예시: 로그인 후 7~30일
  5. 서버에서 기기별 세션을 조회하고 개별 또는 전체 폐기할 수 있도록 관리한다.
  6. localStorage에는 직원 연락처, 근무지, GPS 및 근태 정보와 같은 개인정보를 저장하지 않는다.
  7. 공용 기기에서는 로그인 유지 기능을 기본적으로 사용하지 않도록 한다.
  8. 민감한 작업이나 장기 미사용 후에는 Passkey 등의 수단으로 다시 인증하도록 한다.
  9. 로그인 시도 횟수 제한, 실패 횟수 제한 및 비정상 접근 탐지 기능을 추가한다.

관리자 로그인 ​

관리자 로그인은 서버에서 Google/Supabase 사용자와 admin_users 권한을 다시 확인하므로 현재 근무자 로그인 방식보다는 상대적으로 안전하다.

다만 관리자 로그인에도 무기한 세션 유지보다는 유휴 만료와 절대 만료를 적용하고, 중요 관리 기능을 실행할 때 재인증을 요구하는 것이 적절하다.

결론 ​

현재 문서의 “로그인 상태에 정해진 만료 시간을 두지 않는다”는 정책은 특히 근무자 인증 구현과 결합될 경우 위험도가 높다.

가장 우선해야 할 조치는 단순히 만료 시간을 추가하는 것이 아니라, employeeId 기반 인증 구조를 서버가 발급하고 검증하며 폐기할 수 있는 세션 기반 인증 구조로 교체하는 것이다.
